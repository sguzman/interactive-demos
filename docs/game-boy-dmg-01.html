Nintendo Game Boy DMG-01: one handheld, many machines

The original Game Boy looks almost aggressively simple. Put in four AA batteries, slide in a

cartridge, turn it on, press buttons, watch a greenish screen, hear a tiny speaker.

That simplicity is real at the product level. It is also deceptive.

A single button press can cross all of these layers:

finger
-> plastic button
-> conductive contact
-> electrical matrix
-> JOYP register
-> game logic
-> memory
-> PPU or APU state
-> LCD pixel or speaker waveform

The machine is easiest to understand when those layers stay separate long enough to see how they

connect.

This guide treats the original monochrome Nintendo Game Boy, model DMG-01, as the canonical

specimen. Game Boy Pocket, Light, Color, Advance and later descendants are related products, not

silent additions to the base machine.

There is another important boundary. The DMG-01 existed for long enough to accumulate multiple

board revisions and component substitutions. A concrete reconstruction can use one representative

configuration, but "DMG-01" does not mean one immutable internal bill of materials.

The goal here is therefore not to memorize chips. It is to follow the machine.

1. Start with the object in your hands

The Game Boy is first a physical product.

The front gives you:

  • a reflective LCD;
  • D-pad;
  • A and B;
  • Start and Select;
  • speaker opening;
  • power indicator;
  • contrast and volume controls.

The rear gives you:

  • cartridge slot;
  • battery compartment;
  • battery door.

Around the edges are the power, headphone and link interfaces.

Open the enclosure and the product separates into several physical assemblies rather than one

monolithic motherboard.

A useful high-level anatomy is:

front shell + controls
rear shell + battery/cartridge access
LCD/control board
main CPU board
DC/DC converter board
headphone-jack board
speaker
removable cartridge

That already teaches an important lesson: one logical function does not necessarily live on one

physical board.

The audio system, for example, crosses the custom SoC, the mainboard analog section, a physical

volume control, the separate headphone board and the speaker mounted with the front assembly.

Likewise, the controls are physical objects in the shell, electrical contacts on the front board

and software-visible state inside the custom chip.

2. Powering the Game Boy also participates in reset

The DMG can take energy from four AA cells or an external DC source.

That sounds like a trivial detail until the source path is traced.

The external jack participates in source selection. Inserting external power disconnects the

battery feed. From there, the power switch does more than simply connect the battery to the circuit.

The representative electrical reconstruction shows a DPDT switch whose second pole participates in

reset sequencing.

So the actual startup story is closer to:

battery or external DC
-> source-selection behavior
-> power/reset switch
-> raw VCC
-> separate DC/DC converter
-> regulated VDD + negative VEE
-> oscillator / reset release
-> running electronics

The negative rail matters because the original LCD requires a bias supply quite different from the

main logic supply.

That gives us a useful distinction:

energy source present
!=
logic rail valid
!=
LCD bias valid
!=
reset released
!=
system running

A machine that "has power" in one sense can still be dead in another.

3. The chip called the CPU is larger than the CPU

On the representative mainboard, the large custom package is commonly called the Game Boy CPU.

That is convenient shorthand, but it hides an important architectural fact.

The DMG-CPU package is a custom system-on-chip. Inside it sits the instruction-executing CPU core

that reverse-engineering literature calls the SM83, but the package also contains or coordinates

much more of the console:

  • PPU logic;
  • APU logic;
  • timers;
  • interrupt control;
  • serial/link logic;
  • joypad interface;
  • DMA;
  • clock/reset logic;
  • bus/decode logic.

So:

DMG-CPU package
!=
SM83 CPU core
!=
instruction set

This is not pedantry. It determines how we interpret every later diagram.

When software writes the LCD-control register, for example, it is not talking across the board to a

separate graphics chip. It is addressing logic integrated into the same custom system.

The representative board uses a 4.194304 MHz crystal. Internal logic derives other timing

domains and phases from that master clock.

Again:

master oscillator
!=
derived clock
!=
machine cycle
!=
instruction duration

The machine contains many notions of time even though it begins from one physical oscillator.

4. A memory map is not a wiring diagram

The SM83 sees a 16-bit address space.

It includes familiar-looking regions for cartridge ROM, video RAM, work RAM, I/O registers and

other state.

It is tempting to draw that as one big rectangle and imagine that the hardware is physically laid

out in the same way.

It is not.

The representative DMG board already proves this.

Work RAM is one external SRAM on the system bus.

Video RAM is another external SRAM connected through a separate video-memory interface.

OAM and HRAM belong to integrated SoC state.

Cartridge ROM is not even part of the console. It arrives through a removable module.

And E000-FDFF is an alias of work RAM rather than another memory chip.

So one CPU-visible map overlays several physical realities:

CPU address
-> decode
-> subsystem / bus
-> physical storage or register

Two address ranges can point to the same storage.

One address range can point to different physical cartridge banks depending on mapper state.

And an address can remain logically valid while the CPU is temporarily forbidden from accessing

the underlying resource.

That last case becomes crucial in the graphics system.

5. The cartridge becomes part of the computer

The cartridge is a particularly rich boundary because it is simultaneously:

  • a physical object;
  • a PCB;
  • an electrical bus participant;
  • a ROM/RAM container;
  • sometimes a stateful memory controller;
  • sometimes a battery-backed device;
  • sometimes a clocked peripheral;
  • the carrier of the program.

The console owns the 32-contact slot and its signals.

The cartridge owns whatever hardware is behind that interface.

A simple cartridge can map a small ROM almost directly into the CPU-visible cartridge windows.

A larger cartridge introduces a memory bank controller, or MBC.

Now a write into an address range normally described as "ROM" may not be an attempt to modify ROM

at all. It may instead change the mapper's internal state.

The effective physical ROM address becomes something like:

CPU address
+ mapper registers
+ cartridge wiring
+ ROM geometry
-> physical ROM location

Different MBC families change the rules.

MBC1 combines bank registers and operating modes.

MBC2 contains its own small 4-bit RAM.

MBC3 adds a real-time clock that can continue running from a cartridge battery while the Game Boy

itself is switched off.

MBC5 extends the ROM-bank number and can appear in rumble-capable variants.

That produces one of the most interesting system-boundary facts in the machine:

A removable cartridge can contain state and time that outlive the host's own powered state.

The "software" is therefore not cleanly separable from cartridge hardware.

6. What really happens when you press A

The Game Boy has eight obvious gameplay controls, but software does not receive eight independent

button bits.

The buttons form a 2×4 active-low matrix.

Two groups share four result lines:

  • action buttons;
  • D-pad directions.

Software selects which group it wants to observe and then reads the lower four bits of the JOYP

register.

A complete input trace is:

finger presses A
-> plastic A button moves
-> contact closes
-> electrical matrix changes
-> software selects action-button group
-> JOYP lower bit goes low
-> software observes input

"Active-low" simply means that the electrically asserted state is represented by zero rather than

one.

The important engineering point is that observation depends on selection and timing.

A physical button can be held while software selects the other matrix group and therefore does not

currently observe that control through the lower nibble.

The joypad interrupt is also based on a transition of the electrical/register lines, not on an

abstract semantic event called "button pressed."

This gives us a clean separation:

physical press
!=
contact state
!=
electrical line
!=
register state
!=
game action

7. A pixel is produced over time

The original Game Boy is not best understood as a machine with a finished framebuffer that is sent

to the display all at once.

Its PPU constructs the visible image progressively.

Each frame contains 154 scanlines. The first 144 are visible; the remaining ten form VBlank.

A visible line cycles through several PPU modes.

Mode 2: object search

The PPU searches OAM for objects relevant to the current scanline.

CPU access to OAM is blocked.

Mode 3: pixel transfer

The PPU fetches the graphics data required to produce pixels.

CPU access to both VRAM and OAM is blocked.

Mode 3 is not one rigid duration. It can be lengthened by conditions such as horizontal scroll,

window startup and object fetches.

Mode 0: HBlank

The remaining time in the fixed 456-dot scanline becomes HBlank.

Mode 1: VBlank

After the 144 visible lines, the PPU enters VBlank.

The important idea is this:

scanline duration fixed
while
pixel-transfer duration variable
therefore
HBlank absorbs the difference

Inside pixel transfer, the PPU does not simply look up "the final pixel."

Background/window data and object data pass through separate fetch/FIFO machinery before final

composition.

A useful causal chain is:

VRAM + OAM + PPU registers
-> tile/object fetch
-> background FIFO + object FIFO
-> priority/transparency
-> DMG palette mapping
-> LCD output signals
-> front-board driver electronics
-> physical LCD pixel

That is why a strong interactive model should let you follow one pixel, not merely show a running

emulator screen.

8. Mapped memory can still be unavailable

The PPU introduces a distinction that ordinary memory diagrams hide.

VRAM still has addresses during mode 3.

OAM still has addresses during modes 2 and 3.

But the CPU cannot use them as ordinary memory during those intervals.

So:

mapped
!=
accessible now

This becomes even more dramatic with OAM DMA.

Writing FF46 starts a hardware-assisted transfer of 160 bytes into OAM.

On the original DMG, the CPU loses ordinary access to the wider memory system during that transfer;

HRAM remains the practical region from which software can execute the waiting routine.

DMA is therefore not just "copy 160 bytes faster."

It is a temporary reorganization of who owns the relevant transfer path.

CPU writes DMA request
-> DMA engine becomes active
-> source reads + OAM writes
-> CPU ordinary access restricted
-> PPU may contend for OAM
-> transfer completes

This is a good place to stop thinking of the Game Boy as a collection of memory addresses and start

thinking of it as a timed resource-sharing machine.

9. A sound crosses digital and analog worlds

The DMG has four integrated sound channels:

1. pulse with sweep;

2. pulse;

3. programmable wave;

4. noise.

Each begins as digital state.

Counters, duty patterns, envelopes, a wave table or an LFSR generate discrete channel amplitudes.

Those amplitudes then cross a boundary into analog electronics through per-channel DAC behavior.

From there:

digital channel
-> DAC
-> left/right routing
-> electronic APU output level
-> analog filtering
-> board-level audio path
-> physical volume wheel
-> amplifier
-> speaker or headphones

Two controls that are easy to conflate are actually different.

NR50 changes electronic output scaling inside the APU path.

The physical volume wheel is a separate analog control farther downstream.

Likewise, the Game Boy has stereo-capable internal/headphone routing, but the built-in speaker is

one mono transducer.

So:

stereo-capable audio system
!=
stereo built-in speaker

A cartridge can even feed an analog VIN signal into the console audio path, another case where the

removable module crosses what looks like a clean host/peripheral boundary.

10. Interrupts, timers and the link cable

The same clocked machine also has several smaller control systems.

An interrupt requires at least three distinct concepts:

  • source requested;
  • source enabled;
  • global CPU interrupt permission.

A pending request is not the same thing as a serviced interrupt.

The programmable timer likewise derives slower events from the machine's timing system rather than

owning a separate oscillator.

The serial link adds an especially interesting distributed-system problem.

One Game Boy can provide the serial clock.

The other can wait for externally supplied clock edges.

So two otherwise similar peers can temporarily have different timing roles:

link participant
!=
clock owner

This is a tiny but genuine example of synchronization between machines.

11. There is no single immutable Game Boy inside

A retail model number is not a bill of materials.

Real DMG-01 units have been observed with different mainboard revisions, LCD-board revisions,

converter boards, jack boards, CPU markings, SRAM parts and supplier combinations.

That means these are different identities:

Game Boy DMG-01
board revision
component role
component part number
component instance
supplier
date code
observed console configuration

For a public reconstruction, we therefore need a declared representative internal profile.

The current Engineering model favors DMG-CPU-06 and DMG-LCD-06 because high-quality

revision-specific board reconstructions exist for them.

That does not mean launch units looked exactly like that inside.

A visual model becomes more honest, not less useful, when it says which physical revision it is

showing.

12. Failure reveals the architecture

Repair documentation is valuable because a failed machine forces subsystem boundaries into the

open.

Take "does not power on."

That symptom could originate in:

  • batteries;
  • corroded contacts;
  • source-selection path;
  • power/reset switch;
  • DC/DC converter;
  • downstream electronics.

A useful diagnosis therefore walks the path and gathers discriminating evidence rather than

immediately replacing the most dramatic chip.

Cartridge failures have the same structure.

A known-good cartridge helps separate console-side and cartridge-side hypotheses.

Display lines can point toward the screen/interconnect path.

Speaker failure should be separated from headphone failure because those outputs share some

upstream audio state but diverge in physical hardware.

Nintendo's historical service system also included formal bulletins for revision- or

serial-number-specific issues and required post-repair verification.

One preserved procedure specifies extended burn-in after repair before the unit is returned to the

customer.

That gives us a final service distinction:

repair action completed
!=
repair verified

Modern restorers may choose techniques that Nintendo service centers did not use. Those can be

excellent methods, but historical OEM repair and modern restoration should remain separate evidence

classes.

13. One action crosses the whole machine

Now the layers can be reassembled.

Press A in a running game:

finger
-> button
-> contact
-> matrix
-> JOYP
-> software
-> graphics/audio state
-> PPU/APU
-> electrical output
-> LCD/speaker
-> human perception

Insert a cartridge:

physical module
-> connector
-> bus
-> mapper state
-> memory window
-> CPU instruction/data

Turn the system on:

energy
-> source selection
-> switch/reset
-> converter rails
-> oscillator
-> SoC
-> cartridge/software
-> pixels + sound

None of these chains belongs to one engineering domain.

That is what makes the DMG-01 such a useful specimen.

The product is simple to use because the layers are tightly coordinated.

It is interesting to study because understanding it requires keeping those layers distinct.

14. What the interactive specimen should let you do

The eventual interactive model should begin as a recognizable assembled Game Boy, not as a

schematic.

From there, the reader should be able to switch among several semantic views:

  • Product;
  • Exploded;
  • Power;
  • CPU / memory;
  • Cartridge;
  • Input;
  • PPU / LCD;
  • APU / audio;
  • Service.

The most important interactions should be causal traces.

A visitor should be able to press A and watch the control move, the contact close, JOYP change and

a deterministic demo react.

They should be able to follow a CPU address into the cartridge and watch an MBC select a physical

bank.

They should be able to pause the PPU, inspect a fetcher/FIFO state and watch a pixel arrive at the

LCD.

They should be able to start OAM DMA and see why the CPU's access rights change.

And they should be able to enter a service scenario in which tests narrow a fault hypothesis rather

than turning repair into a guessing game.

The browser visualization will necessarily simplify some geometry and timing for readability.

Those simplifications remain presentation or reconstruction state. They do not become new facts

about Nintendo's production hardware.

15. What is known, reverse-engineered and reconstructed

The Game Boy has an unusually rich evidence surface.

The canonical corpus separates:

  • Nintendo OEM service/electrical material;
  • Nintendo developer documentation;
  • maintained community technical references;
  • photographed hardware populations;
  • board reverse engineering;
  • die reverse engineering;
  • modern community repair guidance;
  • Engineering synthesis.

That hierarchy matters.

A transistor-level reverse engineering result may be extremely precise and still not be a Nintendo

manufacturing document.

A Nintendo programming manual may be authoritative about a software-visible interface while still

being later than the 1989 launch hardware.

A photographed 1992 unit proves that one board combination existed. It does not prove that all

1992 units used it.

And a beautifully rendered 3D mainboard remains a reconstruction unless its dimensions were

actually established.

The useful rule is simple:

Precision in presentation must never be mistaken for stronger provenance.

16. The integrated machine

The Game Boy's elegance does not come from having only a few parts.

It comes from making many distinct layers cooperate so reliably that the player barely notices the

handoffs.

The button feels immediate even though it crosses mechanics, contacts, matrix selection, registers

and software.

The image feels continuous even though the machine constructs it one timed line at a time while

ownership of VRAM and OAM changes beneath the CPU.

The cartridge feels like "the game" even though it may contain its own RAM, controller, battery,

clock and peripherals.

The sound feels like one output even though it crosses counters, DACs, analog mixing, physical

volume control and a speaker.

That is the right way to read the DMG-01:

one intimate product
made from several coupled machines
